# Recording domain knowledge

## Locate before creating
Read GLOSSARY-MAP.md when present and follow the relevant context link. Otherwise use
an existing relevant GLOSSARY.md. If neither exists, propose a suitable location only
when there is useful resolved vocabulary and writing is within scope. No hierarchy is
created simply because a convention is absent. Ask for context choice when available
materials cannot resolve it and the choice changes meaning.

## Separate permission from format
First decide whether the requested task permits writes. Without that scope, give the
proposed text in the response. With writing authorized, use existing project format;
only when no suitable format exists use the bundled glossary template. This ordering
prevents a missing format from being mistaken for permission to create a file.

Keep glossary entries short and specific to the domain. General programming vocabulary
usually needs no entry. Capture resolved definitions promptly without marking unresolved
business rules agreed. Rich relationships/invariants and examples belong in the established
capability/spec/domain-model artifact; do not create another duplicate source automatically.

## ADR branch (read when a decision merits recording)
Offer an ADR when reversal is meaningfully costly, context would otherwise surprise future
readers, and a real alternative was rejected for a reason. If one is absent, a lighter note
usually suffices, subject to the project's own mandatory conventions. Check existing ADR
locations/numbering and preserve the project's approval/status workflow. Include context,
decision, relevant alternatives and consequences in the established format. An available
ADR Skill can help but is not required; discussing a decision does not make an ADR accepted.
